# ContentGuard 性能测试报告

> **报告性质：** 项目阶段性性能测试记录\
> **测试工具：** Locust 2.47.0、Python / FastAPI\
> **测试对象：** ContentGuard 内容审核任务创建接口\
> **接口：** `POST /api/v1/moderation/tasks`\
> **测试环境：** 本机 Windows 开发环境\
> **数据口径：** 本报告将 Locust
> 截图及进程资源采样中的实测值，与基于这些数据得出的分析结论分开记录。

------------------------------------------------------------------------

## 1. 测试目标

本次测试围绕 ContentGuard 的任务创建接口开展，目标是：

1.  观察并发用户增加时接口的响应时间、吞吐量和失败情况。
2.  通过 200 用户并发场景，观察 Locust 与 FastAPI 进程的 CPU
    累计时间和内存变化。
3.  通过持续负载测试，观察响应性能和进程资源是否出现明显恶化。
4.  将测试过程、实测数据、分析结论及测试限制沉淀为项目文档。

## 3. 指标定义与统计口径

  -----------------------------------------------------------------------------------------
  指标                    含义                     本报告使用方式
  ----------------------- ------------------------ ----------------------------------------
  Requests                请求总数                 记录该轮累计请求量

  Failures                失败请求数               观察是否出现请求失败

  Average                 平均响应时间             观察整体平均响应耗时

  Median                  中位响应时间             观察典型请求耗时

  P95                     95 分位响应时间          观察较慢请求的尾部表现

  P99                     99 分位响应时间          观察更靠后的尾部请求表现

  Min / Max               最小 / 最大响应时间      观察响应时间范围

  Current RPS             截图时刻的当前请求速率   仅作为瞬时值记录，不作为整轮平均吞吐量

  CPUSeconds              进程累计 CPU 时间        用采样区间首尾差值观察进程 CPU 消耗

  MemoryMB                进程 Working Set 内存    用采样区间首尾值观察内存变化
  -----------------------------------------------------------------------------------------

**重要口径说明：** Locust 页面中的 Current RPS 是当前速率，不是整轮平均
RPS。没有完整时间序列或整轮统计时，不将它写成平均吞吐量。进程 CPUSeconds
是累计 CPU 时间，不是 CPU 使用率。

## 5. 200 用户并发资源监控

### 5.1 实测数据

在 200 用户并发场景下，对 Locust 与 FastAPI 进程进行约 115
秒的采样。以下为采样区间首尾值：

  指标                   Locust（PID 95888）   FastAPI（PID 97740）
  -------------------- --------------------- ----------------------
  内存起始值                        66.80 MB              110.66 MB
  内存结束值                        67.31 MB              119.69 MB
  内存净变化                        +0.51 MB               +9.03 MB
  CPU 累计时间起始值                 55.38 s                29.12 s
  CPU 累计时间结束值                 63.47 s                36.25 s
  CPU 累计时间增量                   +8.09 s                +7.13 s

> 以上为约 115 秒采样窗口内的首尾差值。Working Set
> 可能因运行时内存管理和操作系统回收而波动。

### 5.2 数据分析

-   Locust 内存净变化较小，采样期间大致维持在 67 MB 左右。
-   FastAPI 内存增加约 9.03 MB，期间存在波动。
-   两个进程的 CPU 累计时间均增加，说明两个进程在采样期间都消耗了 CPU
    时间。
-   CPU 累计时间增量不能直接当作整机 CPU
    百分比；如需计算单逻辑核心归一化平均值，应明确采样时长和计算口径。
-   ContentGuard
    当前使用进程内字典保存任务，创建任务会使数据持续累积，因此 FastAPI
    内存增长可能与任务数据增加有关，不能单凭本次数据判定内存泄漏。

### 6.4 稳定性数据分析

**请求性能：**

-   本轮统计共记录 35,616 次请求，失败数为 0。
-   Average 为 1.87 ms，Median 为 2 ms。
-   P95 为 3 ms，P99 为 4 ms。
-   Max 为 28 ms，说明至少有个别请求明显慢于 P99
    所代表的范围，但整体统计仍显示尾部响应时间较低。
-   Current RPS 为 50，仅代表截图时刻。

**内存：**

-   Locust 内存从 65.39 MB 变化到 65.54 MB，净变化 +0.15 MB。
-   FastAPI 内存从 100.53 MB 变化到 108.96 MB，净变化 +8.43 MB。
-   FastAPI 内存有波动，但在本次约 10
    分钟采样窗口内没有观察到持续快速增长。
-   由于任务数据保存在内存字典中，任务数量累积可能带来正常内存增长；本次测试不能单独证明不存在内存泄漏。

**CPU：**

-   Locust CPU 累计时间增加 26.15 秒。
-   FastAPI CPU 累计时间增加 22.93 秒。
-   以约 597 秒采样窗口计算，分别约为单逻辑 CPU 核心时间的 4.38% 和
    3.84%。这只是按进程累计 CPU 时间差计算的采样区间平均值，不是整机 CPU
    利用率，也不是瞬时值。

### 6.5 稳定性阶段性判断

在本次约 10 分钟的资源采样窗口和对应的 Locust 统计结果中：

-   请求失败数为 0；
-   平均响应时间、P95、P99 均保持在较低水平；
-   Locust 内存基本稳定；
-   FastAPI 内存有约 8.43 MB 的净增长，但未观察到持续失控增长；
-   两个进程的 CPU 累计时间持续增加。

因此，**本轮测试未观察到明显的请求性能衰减或进程资源异常**。但由于资源采样不足完整
12
分钟，且没有完整的响应时间随时间变化曲线，本结论应表述为阶段性结论，而不是对长期稳定性作出保证。

## 7. 综合结论

### 7.1 已有数据支持的结论

1.  前四轮并发测试中，记录的失败请求数均为 0。
2.  前四轮平均响应时间约为 1.85～2.1 ms，P95 为 2～3 ms。
3.  200 用户并发资源采样窗口内，Locust 内存净变化约 +0.51 MB，FastAPI
    内存净变化约 +9.03 MB。
4.  稳定性测试 Locust 统计记录 35,616 次请求、0 次失败，Average 1.87
    ms、P95 3 ms、P99 4 ms。
5.  稳定性测试资源采样窗口内，Locust 内存净变化约 +0.15 MB，FastAPI
    内存净变化约 +8.43 MB。

### 7.2 当前不能据此得出的结论

-   不能据此确定 ContentGuard 的最大并发容量或生产环境承载能力。
-   不能把 Current RPS 当作整轮平均 RPS。
-   不能仅凭进程 CPU 累计时间推断整机 CPU 利用率。
-   不能仅凭约 10 分钟的内存首尾值证明不存在内存泄漏。
-   不能把本机简单 POST
    场景的结果外推到多接口、复杂业务逻辑、真实网络或生产部署环境。

## 8. 测试限制与改进建议

### 8.1 当前限制

1.  测试在本机 Windows 开发环境执行，Locust 与 FastAPI
    运行在同一台机器上，压测工具本身也会消耗本机资源。
2.  当前主要覆盖任务创建 POST
    接口，没有同时覆盖任务查询、人工审核等业务流程。
3.  ContentGuard
    使用进程内字典保存任务，任务数据会随请求持续累积；服务重启后数据会丢失。
4.  当前资源采集主要包含两个 Python 进程的 Working Set 和累计 CPU
    时间，未记录系统整体 CPU、系统内存、磁盘 I/O、网络等指标。
5.  稳定性资源 CSV 覆盖约 9 分 57 秒，不是完整 12 分钟。
6.  部分轮次只保留了截图指标，没有完整的时间序列和统一测试时长。

### 8.2 后续改进

1.  增加任务查询和人工审核接口的混合业务场景，避免只测试单一 POST 接口。
2.  使用固定测试数据规模或设计任务清理机制，区分业务数据累积与异常内存增长。
3.  延长稳定性测试时间，并保存完整资源和响应时间时间序列。
4.  增加系统级 CPU、内存、磁盘和网络监控。
5.  记录整轮平均 RPS、分阶段 P95/P99 和失败率，分析性能是否随时间变化。
6.  在确认基线后，再开展瓶颈定位、代码优化和优化前后对比测试。
