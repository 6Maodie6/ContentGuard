# ContentGuard 性能测试与关键词匹配优化报告

**项目：** ContentGuard 内容审核模拟系统  
**实验范围：** Locust 接口压测、资源监控、稳定性观察、`cProfile` 函数分析、关键词匹配算法对比、V1 正式实现微基准  
**测试环境：** Windows 11、Python 3.13.9；FastAPI、pytest 9.2.0、Locust 2.47.0  
**数据说明：** 本报告依据项目实践中已记录的实验输出整理。所有性能数据均为本机测试结果，不代表生产环境容量。

---

## 1. 执行摘要

本阶段围绕 ContentGuard 的审核接口和关键词扫描逻辑开展性能测试与优化评估。

主要结论：

1. Locust 完成了 10、30、100、200 用户四轮本机压测，以及约 10 分钟的稳定性观察。已记录的测试请求失败数均为 0。
2. `cProfile` 显示，模拟审核函数 `classify_content` 被调用 100,000 次，自身累计耗时约 0.032 秒，累计耗时约 0.047 秒。
3. 在 1,003 个关键词的算法实验中，正则方案在“判断风险类别是否命中”的任务上明显快于逐个关键词扫描；AC 自动机也快于逐个扫描，但慢于本次正则实现。
4. 在正式 V1 仅包含两个关键词（`严重违规`、`低风险`）的微基准中，原生字符串 `in` 比预编译正则快约 2.13 倍。
5. 因此，正式 V1 采用原生 `in` 方案；正则和 AC 自动机实验代码保留为算法研究材料，不把大规模关键词实验的结论直接套用到小规模正式逻辑。

**覆盖率说明：** 正则方案接入阶段曾测得全项目语句覆盖率和分支覆盖率均为 100%。随后正式 V1 恢复为 `in` 方案，用户已重新执行全量 pytest 和 coverage 验证，但本报告依据中没有恢复后最终 coverage 表格。因此，本报告不把恢复前的 100% 冒充为恢复后的最终数据。请将最后一次 coverage 输出中的 TOTAL 和 `app/moderation.py` 数据补入第 8 节。

## 3. Locust 接口压测

### 3.1 四轮并发测试

| 轮次 | 用户数 | 启动速率 | 请求数 | 记录的 RPS | 平均响应时间 | P95 | P99 | 失败数 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 10 | 2 用户/秒 | 500 | 4.8 | 1.86 ms | 2 ms | 未记录 | 0 |
| 2 | 30 | 5 用户/秒 | 1,498 | 14.9 | 2.01 ms | 3 ms | 16 ms | 0 |
| 3 | 100 | 10 用户/秒 | 19,896 | 49.7 | 1.85 ms | 3 ms | 4 ms | 0 |
| 4 | 200 | 20 用户/秒 | 25,118 | 98.2 | 2.10 ms | 3 ms | 5 ms | 0 |

**指标口径：** 表中 RPS 来自 Locust 截图中的 Current RPS 瞬时读数，不应解释为整轮平均吞吐量。各轮持续时间和完整统计口径未全部留存，因此不据此计算精确的平均吞吐量。

### 3.2 结果分析

- 四轮测试均未记录失败请求。
- 平均响应时间约在 1.85–2.10 ms 范围内。
- 100 和 200 用户轮次中，P95 分别为 3 ms，P99 分别为 4 ms 和 5 ms。
- 这是本机、单服务、简单审核逻辑下的测试结果，不能据此推断生产环境可支持相同并发规模。

## 4. 资源监控与稳定性观察

### 4.1 200 用户压测期间资源采样

采样窗口约 115 秒。

| 进程 | 内存起始 | 内存结束 | 内存净变化 | CPU 时间增量 |
|---|---:|---:|---:|---:|
| Locust | 66.80 MB | 67.31 MB | +0.51 MB | +8.09 s |
| FastAPI | 110.66 MB | 119.69 MB | +9.03 MB | +7.13 s |

FastAPI 进程内存净增长约 9.03 MB。由于任务数据存储在进程内存中，任务记录累积可能影响内存变化；仅凭一次采样不能判断是否存在内存泄漏。

### 4.2 约 10 分钟稳定性观察

实际采样窗口约 9 分 57 秒（约 597 秒）。

| 进程 | 内存起始 | 内存结束 | 内存净变化 | CPU 时间增量 |
|---|---:|---:|---:|---:|
| Locust | 65.39 MB | 65.54 MB | +0.15 MB | +26.15 s |
| FastAPI | 100.53 MB | 108.96 MB | +8.43 MB | +22.93 s |

按 CPU 时间增量除以采样墙钟时间估算：

- Locust：`26.15 / 597 × 100% ≈ 4.38%`
- FastAPI：`22.93 / 597 × 100% ≈ 3.84%`

这是进程 CPU 时间相对于墙钟时间的单逻辑 CPU 核归一化估算，不是整机 CPU 使用率。

稳定性测试请求统计：

| 指标 | 结果 |
|---|---:|
| 请求数 | 35,616 |
| 失败数 | 0 |
| Median | 2 ms |
| Average | 1.87 ms |
| P95 | 3 ms |
| P99 | 4 ms |
| Min | 1 ms |
| Max | 28 ms |
| 平均响应大小 | 145 B |
| Current RPS | 约 50（瞬时读数） |

**结论：** 在本次约 10 分钟的测试窗口内，没有观察到明显的响应时间持续恶化或请求失败。FastAPI 内存净增长需要结合任务存储增长、垃圾回收及更长时间的观测进一步判断，不能直接定性为内存泄漏。

## 5. cProfile 函数级分析

记录结果：

```text
400002 function calls in 0.057 seconds

ncalls  tottime  percall  cumtime  percall
1       0.010    0.010    0.057    0.057  run_test
100000  0.032    0.000    0.047    0.000  classify_content
200000  0.010    0.000    0.010    0.000  builtins.len
100000  0.005    0.000    0.005    0.000  builtins.isinstance
```

解释：

- `classify_content` 被调用 100,000 次。
- 函数自身累计时间（tottime）约 0.032 秒。
- 函数累计时间（cumtime）约 0.047 秒，平均约 0.47 微秒/次。
- `len` 调用 200,000 次，对应每次分类中的两次长度检查。
- `isinstance` 调用 100,000 次，对应每次分类的一次类型检查。

该结果反映 Python 函数级调用开销，不包括真实 HTTP 网络、服务器调度和完整请求链路，不应当作 API 延迟。

## 6. 关键词匹配算法实验

### 6.1 算法实验一：83 个关键词

数据规模：

- 高风险关键词：42 个
- 低风险关键词：41 个
- 合计：83 个
- 9 组文本，每组 10,000 次；每轮合计 90,000 次调用
- 重复测量 10 次

平均耗时：

| 方案 | 平均耗时 |
|---|---:|
| 逐个关键词扫描（naive） | 0.077356 s |
| 正则（regex） | 0.059764 s |

本轮正则约快 1.29 倍。

### 6.2 算法实验二：1,003 个关键词

数据规模：

- 高风险关键词：502 个
- 低风险关键词：501 个
- 合计：1,003 个
- 9 组文本，每组 10,000 次；每轮合计 90,000 次调用
- 重复测量 10 次

平均耗时：

| 方案 | 平均耗时 |
|---|---:|
| 逐个关键词扫描（naive） | 0.767715 s |
| 正则（regex） | 0.094855 s |

本轮正则约快 8.09 倍。

### 6.3 算法实验三：1,003 个关键词，三种算法对比

测试包含短文本无命中、500 字符长文本无命中、短文本命中、长文本末尾命中、多高风险词、多低风险词、高低风险混合、重叠关键词、重复关键词等场景。

关键词中包含重叠关系，例如：

- `诈骗`
- `诈骗信息`
- `诈骗信息平台`

构建时间：

| 方案 | 构建耗时 |
|---|---:|
| 正则 | 0.000475 s |
| AC 自动机 | 0.000747 s |

正式测量设置：

- 每种算法预热：每个文本 200 次
- 正式测量：10 轮
- 每个文本每轮 1,000 次
- 每轮每种算法合计 9,000 次调用
- 每轮轮换算法执行顺序

平均耗时：

| 方案 | 平均耗时 | 相对 naive |
|---|---:|---:|
| naive | 0.599401 s | 1.00 倍 |
| regex | 0.010341 s | 约 57.97 倍 |
| AC 自动机 | 0.081759 s | 约 7.33 倍 |

本实验中，正则约为 AC 自动机的 7.91 倍速度。

**解释与限制：**

- 本次正则方案的目标是判断高风险或低风险类别是否存在，不枚举全部命中词。
- AC 自动机实现会在 Python 层遍历状态、处理字典和构造匹配结果，存在额外开销。
- 本次结果只适用于本实验实现、关键词集和文本集，不能推出正则在所有关键词规模、文本分布和匹配需求下都优于 AC。
- 第三轮每轮 9,000 次调用，与前两轮每轮 90,000 次调用不同，不能直接比较各轮绝对耗时；应比较各轮内部相对基线的加速比。

## 7. 正式 V1：`in` 与预编译正则公平微基准

### 7.1 实验目标

正式 V1 只有两个关键词：

- 高风险：`严重违规`
- 低风险：`低风险`

本实验比较：

- A 组：原始 V1，使用 Python 原生字符串 `in`。
- B 组：预编译正则表达式，使用 `Pattern.search()`。

两种实现放在独立基准脚本中，不修改正式服务代码来运行实验。两组使用同一批输入，并先进行分类结果一致性验证。

### 7.2 测试设置

- 8 种文本场景：普通文本、单一风险词、两类风险词同时出现、较长文本、长文本末尾命中等。
- 预热：每种方案 1,000 轮（每轮遍历全部测试文本）。
- 正式测量：7 轮。
- 每轮每种方案调用：160,000 次。
- 两组轮换执行顺序。
- 统计每次调用耗时的中位数。
- 正则在模块加载时预编译，测量不包含重复编译成本。

### 7.3 实验结果

| 指标 | `in` 方案 | 正则方案 |
|---|---:|---:|
| 单次调用耗时中位数 | 0.1106 μs | 0.2353 μs |
| 最快一轮 | 0.1076 μs | 0.2276 μs |
| 最慢一轮 | 0.1274 μs | 0.2642 μs |

`in` 方案约快 2.13 倍。

正确性验证通过：全部测试输入的两个方案返回结果一致。

### 7.4 工程决策

正式 V1 恢复为原生 `in` 方案，理由：

1. 当前只有两个关键词，原生字符串查找足以满足需求。
2. 实测 `in` 方案中位数耗时更低，约快 2.13 倍。
3. `in` 代码更直接，阅读和维护成本更低。
4. 正则方案在 83 和 1,003 关键词实验中表现出扩展价值，但这不能证明它适合当前只有两个关键词的正式 V1。

这次决策不是否定正则，而是依据真实业务规模选择更合适的实现。正则和 AC 自动机实验代码可以继续保留在 `performance/` 目录中，作为算法对比和技术储备。

## 9. 局限与后续改进方向

1. 所有 Locust 数据均为本机实验，不是生产环境容量评估。
2. RPS 记录为瞬时 Current RPS，不能替代整轮平均吞吐量。
3. API 测试场景和服务逻辑较简单，尚未覆盖真实外部依赖、数据库、复杂业务数据和生产部署拓扑。
4. 进程内 `task_store` 会随任务创建而累积；需要区分业务数据增长与内存泄漏。
5. 关键词算法实验的结果依赖关键词规模、文本分布、是否需要枚举全部命中和具体实现。
6. 后续可以在相同服务配置、相同 Locust 用户数和运行时长下，对 API 层优化前后进行对照压测；需要记录完整统计窗口、失败率、P95/P99、资源和任务数据增长。

## 10. 面试表达参考

我在一个基于 FastAPI 的内容审核模拟项目中做过接口性能测试和关键词扫描优化评估。

首先使用 Locust 从 10 到 200 用户进行多轮压测，并做了约 10 分钟稳定性观察，记录请求数、响应时间分位数、失败数以及服务进程的内存和 CPU 时间。

随后使用 `cProfile` 分析函数级开销，并对 naive、正则和 AC 自动机做关键词匹配微基准。在 1,003 个关键词、只判断风险类别是否命中的实验中，正则方案明显快于逐个扫描。

但把正则接入正式 V1 后，我又针对实际只有两个关键词的场景，重新比较原生 `in` 和预编译正则。两者结果一致，但 `in` 中位数耗时为 0.1106 微秒，正则为 0.2353 微秒，`in` 约快 2.13 倍。因此我把正式实现恢复为更简单的 `in`，保留正则和 AC 的实验结果。这让我能够根据实际数据而不是技术偏好做优化决策。
