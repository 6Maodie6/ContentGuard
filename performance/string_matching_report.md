# ContentGuard 关键词匹配算法性能对比报告

> 建议保存位置：`performance/string_matching_report.md`\
> 实验范围：逐个扫描（Naive）、正则扫描（Regex）、Aho-Corasick（AC
> 自动机）\
> 数据来源：三轮本地 Python 微基准实验的实际终端输出。

## 1. 实验目的

ContentGuard
使用关键词识别模拟内容风险。本实验比较三种关键词匹配方案，验证分类正确性，并观察关键词规模和文本场景变化对搜索耗时的影响。

三种方案：

1.  **逐个扫描**：逐个检查关键词是否出现在文本中。
2.  **正则扫描**：将关键词编译为正则表达式，再执行匹配。
3.  **AC 自动机**：使用 Trie 和 Failure Link 构建多模式匹配自动机。

本报告中的结果是本机微基准数据，不代表生产环境容量或 API 性能。

## 2. 统一业务规则

  命中情况                           分类结果
  ---------------------------------- ---------------------
  命中高风险关键词                   `block` / `high`
  未命中高风险，但命中低风险关键词   `review` / `medium`
  两类关键词均未命中                 `pass` / `low`

高风险优先级高于低风险。同一文本同时命中两类关键词时，最终必须为 `block`
/ `high`。

输入校验要求：

-   非字符串输入抛出 `TypeError`。
-   空字符串抛出 `ValueError`。
-   长度超过 500 个字符抛出 `ValueError`。

## 3. 第一轮：83 个关键词

### 实验设置

-   高风险关键词：42 个。
-   低风险关键词：41 个。
-   总计：83 个。
-   测试文本：9 组。
-   每轮对 9 组文本各执行 10,000 次，共 90,000 次分类。
-   重复测量：10 次。

### 实测结果

首次运行：

  指标            逐个扫描      正则扫描
  ---------- ------------- -------------
  单次耗时     0.077793 秒   0.060122 秒

重复 10 次的平均耗时：

  指标            逐个扫描      正则扫描
  ---------- ------------- -------------
  平均耗时     0.077356 秒   0.059764 秒

正则扫描相对逐个扫描的平均加速比：**1.29 倍**。

### 观察

在 83
个关键词和当前测试文本下，正则扫描比逐个扫描快；重复测试后仍观察到约
1.29 倍的平均优势。

## 4. 第二轮：1003 个关键词

### 实验设置

-   高风险关键词：502 个。
-   低风险关键词：501 个。
-   总计：1003 个。
-   测试文本：沿用原来的 9 组。
-   每轮分类：90,000 次。
-   重复测量：10 次。

### 实测结果

  指标            逐个扫描      正则扫描
  ---------- ------------- -------------
  平均耗时     0.767715 秒   0.094855 秒

正则扫描相对逐个扫描的平均加速比：**8.09 倍**。

### 观察

关键词数量从 83 个增加到 1003
个后，逐个扫描的平均耗时明显增加，正则扫描在该数据集上的优势扩大。该结果仅适用于本轮关键词集合、文本分布和具体实现，不能推断所有正则表达式都具有相同优势。

## 5. 第三轮：三种算法与更丰富的文本场景

### 5.1 实验设置

关键词总数仍为 1003 个：

-   高风险关键词：502 个，包含
    `严重违规`、`诈骗`、`诈骗信息`、`诈骗信息平台` 等。
-   低风险关键词：501 个。
-   三种算法：逐个扫描、正则扫描、AC 自动机。
-   测试文本：9 类场景。
-   每轮每种算法处理 9 组文本各 1,000 次，共 9,000 次分类。
-   重复测量：10 轮。
-   正式测试前，各算法使用相同测试文本预热。
-   每轮轮换算法执行顺序，以降低固定执行顺序造成的偏差。

本轮正则方案分别编译高风险和低风险表达式，并通过 `search()`
判断两类关键词是否存在。它只负责最终分类，不枚举全部匹配词或位置。

### 5.2 测试场景与正确性

  场景                           验证目的
  ------------------------------ ------------------------------
  短文本无命中                   基础搜索
  长文本无命中（500 字符）       无命中扫描
  短文本单命中                   基础命中
  长文本末尾单命中（500 字符）   长文本定位
  多个高风险词                   多次高风险命中
  多个低风险词                   多次低风险命中
  高低风险混合                   验证高风险优先级
  重叠关键词 `诈骗信息平台`      验证前缀重叠情况下的最终分类
  重复关键词                     验证重复出现时的最终分类

终端结果显示：

-   9 类文本场景下，三种算法的最终分类结果一致。
-   整数和 `None` 输入均得到 `TypeError`。
-   空字符串和 501 字符文本均得到 `ValueError`。
-   高风险与低风险同时出现时，最终结果为 `block` / `high`。
-   重叠关键词场景下，三种方案的最终分类一致。

终端输出为"所有场景的分类结果一致"和"异常输入验证通过"。

**正确性范围：**
以上验证覆盖列出的场景和输入边界，并非对所有可能字符串的穷举证明。正则方案判断风险类别是否存在，不承诺返回所有重叠关键词的完整匹配列表。

### 5.3 构建耗时

  构建项目                                       实测耗时
  -------------------------------------- ----------------
  正则表达式编译（高风险、低风险两组）        0.000475 秒
  AC 自动机构建                               0.000747 秒
  逐个扫描                                 无额外索引构建

构建耗时与重复搜索耗时分开统计。正则表达式和 AC
自动机均在正式计时前构建；正式性能测试测量的是复用已构建结构后的分类耗时。

### 5.4 十轮搜索结果

  指标            逐个扫描      正则扫描     AC 自动机
  ---------- ------------- ------------- -------------
  平均耗时     0.599401 秒   0.010341 秒   0.081759 秒
  最快一次     0.570683 秒   0.009770 秒   0.078261 秒
  最慢一次     0.631627 秒   0.011236 秒   0.084527 秒

相对逐个扫描的平均加速比：

  方案                加速比
  ----------- --------------
  正则扫描      **57.97 倍**
  AC 自动机      **7.33 倍**

按平均耗时计算，正则扫描约为 AC 自动机的 **7.91 倍**。

### 5.5 结果分析

在本轮给定的 1003 个关键词和 9 类测试文本中，正则扫描耗时最低，AC
自动机快于逐个扫描但慢于正则方案。

可能的实现层面原因：

-   当前 AC 自动机是 Python
    层实现，搜索过程包含字符遍历、字典查找、Failure Link
    回退和匹配结果收集。
-   正则匹配由 Python 底层正则引擎执行。
-   本轮正则只判断高风险、低风险是否存在，不需要枚举所有匹配项。

因此，结果反映的是**具体实现与具体业务目标**下的实测表现，不能简单归结为某一种算法在所有情况下都更快。

## 7. 当前工程结论

基于目前完成的实验：

1.  对 ContentGuard 当前模拟审核规则，建议暂时保留正则扫描实现。
2.  保留逐个扫描作为简单基准方案，便于后续回归比较。
3.  保留 AC 自动机实验代码，作为多模式匹配技术储备。
4.  不因 AC
    自动机更复杂或更有算法代表性，就直接替换当前实测更快的正则实现。
5.  如果未来需要返回所有匹配词及其位置、关键词规模继续增长、规则结构更复杂，或正则表达式维护成本上升，再评估
    AC 自动机或成熟的多模式匹配库。

## 8. 实验限制与后续改进

本报告结果需要结合以下限制理解：

-   实验运行于本地 Windows + Python 环境，不是生产服务器压测。
-   微基准使用有限数量的人工构造文本，不能代表真实用户内容分布。
-   第三轮增加了多种文本场景，但没有分别输出每类场景的独立耗时，因此不能判断某一具体场景下的算法排名。
-   第三轮正则方案只判断两类风险是否存在；AC
    自动机收集所有命中项，内部执行工作并不完全相同。
-   当前测试没有覆盖所有可能的关键词重叠组合、Unicode
    边界、特殊字符组合或超大规模规则集。
-   `perf_counter()` 微基准可能受到系统后台负载、Python
    运行时和机器配置影响。
-   构建耗时未包含内存占用测量。
-   当前结果不能直接推导 API 的 RPS、响应时间、P95/P99 或生产并发容量。

后续建议：

1.  为每类文本场景单独统计耗时。
2.  增加随机生成文本和更接近真实分布的测试数据。
3.  增加全面的重叠关键词测试，比较所有匹配词和位置，而不仅是最终分类。
4.  测量三种方案的内存占用。
5.  将选定方案接入 FastAPI 后，使用 Locust 对 API 进行优化前后压测，比较
    RPS、响应时间、P95/P99 和错误率。
6.  记录 Python
    版本、操作系统、CPU、关键词集版本和测试脚本版本，提升实验可复现性。
