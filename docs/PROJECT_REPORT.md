# ContentGuard｜项目总结报告

## 1. 项目概述

### 1.1 项目背景
ContentGuard 是一个用于练习测试开发工程能力的模拟内容审核系统。项目构建审核分类逻辑和 HTTP API，并围绕接口功能、业务规则、异常处理、版本变化和性能表现开展测试。重点是实践需求理解、测试设计、自动化执行、差异分析和性能数据解释，不是实现真实内容安全策略。

### 1.2 项目目标
- 搭建可测试的 FastAPI 服务，并分离接口层与审核业务逻辑。
- 使用 pytest 建立自动化测试和数据驱动测试。
- 覆盖输入校验、异常处理和业务状态流转。
- 使用 Diff 思路验证 V1/V2 规则变化。
- 使用 Locust 测量多接口业务链路在不同负载下的表现。
- 通过微基准实验理解关键词匹配方案的适用条件。

### 1.3 技术栈
Python、FastAPI、Pydantic、pytest、FastAPI TestClient、Locust、pytest-html、Allure pytest 插件、Git、GitHub Actions。

说明：工具安装或配置不等于所有功能均已在最终仓库中验证成功。CI 实际运行状态应以 GitHub Actions 记录为准。

## 2. 系统结构与业务设计

### 2.1 主要模块

| 模块 | 职责 |
|---|---|
| `app/main.py` | FastAPI 应用、HTTP 接口及任务状态流转 |
| `app/moderation.py` | V1 内容分类逻辑 |
| `app/moderation_v2.py` | V2 内容分类逻辑，增加新规则 |
| `tests/` | 接口、单元、校验、工作流和 Diff 测试 |
| `data/` | JSON 测试数据 |
| `performance/` | Locust 场景、微基准和性能分析文档 |
| `conftest.py` | 公共测试 fixture |
| `.github/workflows/` | CI 工作流配置 |

### 2.2 审核规则

| 规则 | 预期行为 |
|---|---|
| 输入类型 | 必须为字符串 |
| 内容长度 | 1～500 个字符 |
| 空内容 | 拒绝 |
| 包含“严重违规” | `block`，高风险 |
| 包含“低风险” | `review`，中风险 |
| 同时包含两者 | 严重违规优先，返回 `block` |
| 普通内容 | `pass`，低风险 |

V2 在原有校验和规则基础上增加“诈骗”关键词的高风险拦截。V2 具体函数接口以代码实现为准。

### 2.3 HTTP API 与业务流程

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/moderation/tasks` | 创建审核任务 |
| GET | `/api/v1/moderation/tasks/{task_id}` | 查询审核任务 |
| POST | `/api/v1/moderation/tasks/{task_id}/manual-review` | 人工审核待处理任务 |

主要流程：
1. 客户端提交内容，服务执行分类。
2. `review` 任务进入 `pending`，等待人工审核。
3. `pass` 或 `block` 任务直接进入 `completed`。
4. 客户端通过 task_id 查询任务。
5. 对 `pending` 任务提交人工审核决定。
6. 人工审核完成后状态变为 `completed`。
7. 已完成任务不允许再次人工审核。

任务数据使用进程内字典保存，服务重启后会丢失；当前实现不等同于生产级持久化任务系统。

## 3. 自动化测试设计

### 3.1 测试分层
- 业务逻辑单元测试：直接测试 V1/V2 分类函数。
- 接口测试：通过 TestClient 调用 FastAPI 路由。
- 输入校验测试：验证类型、空值和长度边界。
- 工作流测试：验证创建、查询、人工审核及状态变化。
- Diff 测试：使用相同输入比较不同版本输出。

### 3.2 测试设计维度

| 维度 | 示例 |
|---|---|
| 正常场景 | 普通内容、严重违规、低风险 |
| 边界场景 | 最短有效内容、500 字符、超过 500 字符 |
| 非法输入 | 非字符串、空字符串、非法审核决定 |
| 优先级 | 同时包含高风险与低风险关键词 |
| 资源不存在 | 查询不存在的任务 ID |
| 状态约束 | 已完成任务再次提交人工审核 |
| 版本差异 | V1/V2 对新增规则及既有规则的输出差异 |

### 3.3 pytest、fixture 与数据驱动
项目使用 pytest 组织执行测试，通过公共 fixture 提供 TestClient，减少测试函数重复初始化客户端的代码。数据驱动测试将输入和预期结果从测试逻辑中分离，便于扩展场景；JSON 用于保存结构化测试用例。

### 3.4 异常与状态码
接口测试同时检查响应内容、HTTP 状态码和业务状态。典型异常包括输入不满足业务校验、任务不存在、非法审核决定、已完成任务重复审核，以及框架级请求校验错误。业务层主动抛出的输入错误在接口层映射为 400；任务不存在为 404；已完成任务重复审核为 409；FastAPI/Pydantic 请求校验错误通常为 422。具体以当前代码和测试断言为准。

## 4. Diff 测试与版本验证

Diff 测试使用相同输入分别执行 V1 和 V2，再比较输出差异。重点验证：
- V2 新增“诈骗”规则是否生效。
- 普通内容分类是否保持预期。
- 原有高风险、低风险规则是否发生非预期变化。
- 多关键词同时出现时，输出是否符合各版本规则。

输出不同只说明版本行为存在差异，不自动等于缺陷；需要结合版本需求判断差异是否符合预期。本项目的 V1/V2 是模拟规则版本。

## 5. 性能测试

### 5.1 完整业务链路
Locust 场景按以下顺序执行：
1. POST 创建低风险内容任务，预期进入待人工审核状态。
2. GET 查询该任务。
3. POST 提交人工审核决定。
4. GET 再次查询，确认状态和结果更新。

场景使用创建接口返回的 `task_id` 关联后续请求，并检查状态码和业务响应。用户等待时间配置为 1～3 秒。

### 5.2 第一批多用户测试
以下三轮均持续 3 分钟，用户数顺序为 10、50、30：

| 指标 | 10 用户 | 50 用户 | 30 用户 |
|---|---:|---:|---:|
| HTTP 请求数 | 3,396 | 17,504 | 10,544 |
| 失败数 | 0 | 0 | 0 |
| Average | 1.20 ms | 1.22 ms | 1.16 ms |
| Median | 1 ms | 1 ms | 1 ms |
| P95 | 2 ms | 2 ms | 2 ms |
| P99 | 3 ms | 3 ms | 3 ms |
| Max | 13 ms | 16 ms | 15 ms |
| Current RPS（瞬时） | 20.8 | 96.8 | 59.6 |
| 整轮平均 RPS | 18.87 | 97.24 | 58.58 |

整轮平均 RPS 按总 HTTP 请求数除以 180 秒计算。Locust 的 Current RPS 是瞬时指标，不能与整轮平均 RPS 混淆。

### 5.3 50 用户重复测试

另一次 50 用户、5 users/s、3 分钟测试：

| 接口 | Requests | Fails | Average | P95 | P99 | Max |
|---|---:|---:|---:|---:|---:|---:|
| 创建任务 | 4,402 | 0 | 1.83 ms | 3 ms | 4 ms | 24 ms |
| 查询任务 | 4,402 | 0 | 1.03 ms | 2 ms | 2 ms | 4 ms |
| 人工审核 | 4,402 | 0 | 1.05 ms | 2 ms | 2 ms | 14 ms |
| 最终查询 | 4,401 | 0 | 0.94 ms | 1 ms | 2 ms | 8 ms |
| 聚合 | 17,607 | 0 | 1.21 ms | 2 ms | 3 ms | 24 ms |

整轮平均吞吐量：`17,607 / 180 ≈ 97.82 RPS`。

与此前 50 用户测试相比，请求数、平均响应时间、P95 和 P99 接近，说明相同配置下两次结果具有一定重复性。创建任务接口在该轮测试中平均响应时间和尾延迟略高。

四个 HTTP 请求组成一次业务流程。约 97.82 HTTP RPS 可按四个请求近似折算为约 24.45 次完整业务流程/秒；实际成功流程数应以业务级统计为准。

### 5.4 进程资源观察

测试前后通过 PowerShell 进程信息确认 Locust 和 FastAPI 进程，并记录 CPU 累计时间和 Working Set：

| 指标 | Locust | FastAPI |
|---|---:|---:|
| CPU 时间增量 | 11.30 s | 10.33 s |
| 内存测试前 | 74.60 MB | 50.24 MB |
| 内存测试后 | 70.63 MB | 57.39 MB |
| 内存变化 | 约 -3.97 MB | 约 +6.82 MB |

以 180 秒为窗口，CPU 时间增量除以墙钟时间，Locust 约 6.28%，FastAPI 约 5.74%。这是按单逻辑 CPU 核归一化的累计 CPU 时间比例，不是整机 CPU 使用率或实时 CPU 指标。

FastAPI 内存增加可能与进程内 `task_store` 持续保存任务有关。仅凭一次前后采样不能认定发生内存泄漏。

### 5.5 早期稳定性测试
早期约 9 分 57 秒的稳定性测试记录：
- 请求数 35,616，失败数 0。
- Average 1.87 ms，Median 2 ms。
- P95 3 ms，P99 4 ms，Max 28 ms。
- 测试窗口约 597 秒。
- FastAPI Working Set 增加约 8.43 MB。

该测试窗口内没有观察到明显性能衰减。结论仅适用于当时本机环境和负载配置，不能证明长期运行无内存泄漏。

## 6. 关键词匹配算法实验

### 6.1 多关键词方案对比
在 1003 个关键词的数据集上，对 naive 字符串匹配、正则表达式和 Aho-Corasick 进行独立微基准。场景包括短文本无命中、长文本无命中、单命中、多命中、高低风险混合、重叠关键词和重复关键词。

| 方案 | 平均耗时 |
|---|---:|
| naive | 0.599401 s |
| regex | 0.010341 s |
| Aho-Corasick | 0.081759 s |

该实验设置下，regex 相对 naive 约快 57.97 倍，Aho-Corasick 相对 naive 约快 7.33 倍，regex 相对 Aho-Corasick 约快 7.91 倍。

限制：
- regex 主要判断类别是否存在，Aho-Corasick 会收集匹配项，内部工作量不完全相同。
- 结果受关键词集合、文本样本、Python 实现和测试机器影响。
- 有限样本微基准不能直接代表线上服务性能。
- 算法选择需考虑维护成本、功能目标和实际输入规模。

### 6.2 正式 V1 的 `in` 与预编译 regex 对比
正式 V1 只有少量关键词，因此使用独立脚本比较原始 `in` 判断和预编译正则。测试前验证输出一致，预热后进行 7 轮测试，每轮每方案执行 160,000 次调用，并轮换执行顺序。

| 指标 | `in` | 预编译 regex |
|---|---:|---:|
| 中位平均耗时 | 0.1106 μs/次 | 0.2353 μs/次 |

在该实验中，`in` 约快 2.13 倍。结合当前 V1 关键词数量少、逻辑简单的实际情况，最终保留 `in` 方案。正则和 Aho-Corasick 作为算法实验保留，不将大规模关键词实验结论直接套用到当前 V1。

## 7. 函数级微基准

对任务创建相关操作进行独立微基准，预热 1000 次，每个函数执行 100,000 次：

| 操作 | 总耗时 | 平均耗时 |
|---|---:|---:|
| 内容分类 | 0.010688 s | 0.107 μs/次 |
| UUID 生成 | 0.120522 s | 1.205 μs/次 |
| 状态判断 | 0.004658 s | 0.047 μs/次 |
| 任务组装（含分类和 UUID） | 0.139229 s | 1.392 μs/次 |
| 字典创建及写入 | 0.126197 s | 1.262 μs/次 |

`build_task` 包含内容分类、UUID 生成、状态判断和任务字典组装，不能将各项耗时简单相加。字典写入基准每次新建字典再写入一条任务，不代表真实服务持续增长的 `task_store` 写入开销。这些数据用于理解函数级开销，不等于 HTTP API 响应时间，也不能单独证明系统瓶颈。

## 8. 综合结论

### 8.1 功能与业务测试
项目围绕审核分类、输入校验、任务查询、人工审核和状态限制建立多层测试，通过数据驱动、参数化和异常场景设计验证主要业务规则及接口行为。

### 8.2 Diff 测试
通过相同输入对比 V1/V2 输出，验证规则升级差异。需要结合需求判断差异是否符合预期，而不是将所有差异都视为缺陷。

### 8.3 性能测试
本机环境下，50 用户完整业务链路两次测试均未记录失败请求，聚合 P95 为 2 ms、P99 为 3 ms，整轮平均 HTTP 吞吐量约 97 RPS。重复测试结果接近，形成当前环境下的基准数据。

### 8.4 算法实验
不同算法在不同关键词规模和目标下表现不同。当前 V1 少量关键词场景保留 `in` 判断，体现根据实际需求选择简单方案的原则。

## 9. 项目局限与后续改进

当前项目是本地模拟服务和测试实践项目，存在以下局限：
1. 任务存储使用进程内字典，不具备持久化能力，也未验证多进程共享状态。
2. 审核关键词和风险级别是模拟规则，不代表真实内容安全业务规范。
3. 未接入真实 AI 模型，因此不能声称已完成模型准确性、鲁棒性或幻觉测试。
4. 性能测试在本机执行，缺少生产级部署拓扑、网络环境和完整监控，不能外推生产容量。
5. CI 工作流文件已纳入项目结构，但是否成功执行应以 GitHub Actions 实际记录为准。
6. 最新恢复 V1 `in` 方案后的全量测试与覆盖率已由项目开发者重新执行，但本报告未记录未经核实的最终通过数量或覆盖率百分比。

后续可考虑：
- 接入数据库，验证任务持久化、并发访问和数据一致性。
- 完善 CI 自动执行、测试报告归档和失败通知。
- 增加更真实的负载模型、服务端监控和长时间稳定性测试。
- 引入真实 AI 模型后，设计准确性、一致性、鲁棒性和安全性测试。

## 10. 项目收获

通过 ContentGuard，实践了从业务规则理解到测试设计、自动化实现、版本差异验证和性能分析的完整过程。项目不仅关注请求是否成功，也关注业务状态是否正确、异常是否被合理处理、版本升级是否引入非预期变化，以及性能数据是否能在明确测试条件下复现和解释。

项目强调以测试证据支撑结论：记录测试环境、并发配置、请求数量、响应时间分位数、失败率和资源变化，并明确微基准与 API 性能测试的区别，以及本机实验结果的适用边界。
